# AGENTS.md

## Product identity

- The product has one name: **Pomegr**.
- Use `pomegr` for package, repository, and directory identifiers.
- Keep the name provider-neutral. Provider names belong only in adapter-specific configuration and documentation.

## Purpose

Pomegr is a local-first observer for coding-agent sessions and, in the desktop app only, an opt-in dispatcher that starts sessions for repository tasks (product-owner decision, 2026-10-08). Observation stays read-only: it presents real execution metadata and deterministic efficiency signals, and it never writes provider files, attaches to a session, or controls a provider process. Tasks and dispatch are a separate control plane with their own private store, routes, and desktop actions; the observation pipeline neither depends on them nor changes because of them. The task board and dispatcher are specified in `docs/internal/architecture/tasks.md`; describe as available only what that contract says is built. Never imply that a heuristic is an AI judgment or authoritative measurement.

## Collaboration

- The user grants standing permission to use subagents for repository work whenever parallel or independent assessment would improve the result. Do not ask for subagent permission again.
- Default subagents and workflow workers to the cheapest capable model, such as Sonnet, Haiku (Claude), Terra, Luna (Codex). Reserve larger models for stages that genuinely need stronger reasoning, and never leave investigative or probe agents on the session's default model by accident.
- Real provider sessions (`codex exec`, `claude`, a Codex app-server, or similar) may be launched when a fix genuinely needs live evidence, but they are temporary scaffolding. Prefer letting each run finish on its own over killing it mid-turn; a killed run leaves an unfinished turn in the user's catalog. When the fix is done, delete the probe that launched them. Never keep one as a script, a persistent test, or an automated step. Durable tests use synthetic transcripts or an isolated temporary provider home, as in the opt-in `tests/server/providers/codex/native-lock-acceptance.test.mjs`.

## Architecture

- `server/server.mjs` owns discovery, transcript history indexing, parsing, normalization, Git inspection, usage-limit retrieval, and deterministic metrics.
- `app/Dashboard.tsx` renders normalized state and must not access credentials or raw session files.
- `app/api/state/route.ts`, `app/api/sessions/route.ts`, `app/api/home/route.ts`, and `app/api/usage-limits/route.ts` are same-origin proxies to the loopback monitor.
- `scripts/dev.mjs` starts the monitor and web application together.
- Keep provider transcript schemas out of React components.
- Production session, catalog, Home, and usage-limit GETs serve only committed response caches. A request may queue asynchronous hydration, but it must never synchronously acquire, parse, or normalize provider data.
- `GET /api/notifications` serves only the committed, bounded notification projection derived from already committed session-catalog and public-provider-status facts. Notification rules in `server/notifications/` own condition transitions and occurrence identity; the browser renders normalized records and keeps monitor-transport failure in a separate `client:` namespace. No notification GET acquires provider evidence or controls a provider.
- Source read/chunk bounds control upstream acquisition cost only; they must never control the lifetime of already-normalized evidence. Preserve the last known-good revision until a complete replacement validates and commits atomically.
- Keep U1 Acquisition, U2 Normalization, C Commit, D Derivation, P Persistence, S Serving, and F Presentation ownership aligned with `docs/internal/architecture/observation-cache.md`.

## Security and privacy invariants

- The notification response may expose only version, monotonic revision, generation time, catalog/provider-status readiness, a bounded active-session overflow count, and occurrences with an opaque ID; fixed kind, category, severity, lifecycle, action and time-basis values; bounded priority; original occurrence time; delivery eligibility; normalized provider or null; and narrow kind-specific data. `needs_input` carries only a validated normalized session ID and bounded catalog title; provider incident/recovery carries only a fixed health status; client-local `monitor_unreachable` carries no data. Active status or title updates preserve occurrence identity and original time. Private comparison keys, source scopes, provider payloads, paths, credentials, prompts, commands, errors, and arbitrary URLs never cross the boundary. Actions map to fixed local destinations and cannot approve work, authenticate, install, or change a provider. Durable monitor baselines and native delivery claims stay in separate private, versioned, bounded atomic stores; malformed or newer stores cannot be overwritten by routine writes. Native delivery claims an occurrence before OS dispatch, so a crash can lose a toast. Browser-local read markers hold only bounded opaque IDs and times for 30 days, never titles or source fingerprints; reading does not resolve a condition or synchronize with native delivery. See `docs/internal/architecture/observation-cache.md`.
- Desktop notification settings persist only the existing `notifications` boolean and fixed `notificationCategories` booleans (`attention`, `provider_news`, `model_news`) in private desktop settings. One-hour quiet remains memory-only. New news categories default off. Only a trusted main-frame, fixed-key IPC handler can change these settings; browser/LAN clients cannot mutate them. The desktop's committed-feed reader rejects HTTP redirects before sending local authorization elsewhere, and notification actions stay on fixed local routes.

- Usage notifications derive only from fresh, complete, comparable committed account observations. Clock crossing alone never confirms a reset. The fixed `usage_window_reset` and `usage_capacity_restored` kinds carry only a fixed window key, `provider_api`/`local_observation` origin, and an `otherExhausted` boolean; `usage_reset_available` carries only a bounded positive Codex available count. Account usage may additionally expose `resetCredits` with supported/unknown status, count 0–1000 or null, and original observation time. Missing/null is unknown; availability is never redemption eligibility. Never retain or expose credit IDs, titles, descriptions, or redemption payloads, and never consume a reset. Private notification comparison state holds at most one baseline per provider: opaque credential-source filesystem scope, fixed origin, original time, opaque window-set digest, at most sixteen normalized windows (fixed display key, opaque stable identity, percentage, exhaustion, reset time), and nullable bounded count. Out-of-order evidence cannot rewind it; stale/partial/unknown and source changes break comparisons. The fixed usage_authentication_required kind carries empty data and uses provider_news (native Provider updates opt-in, default off), warning severity, and the same fixed Usage limits action. Its private per-provider baseline holds only opaque scope, last attempt/retry times, and a notified flag. Only a later fresh recognized authentication-required attempt after its normal retry can emit once; transient or generic failures never qualify. - Task board and dispatch (product-owner decision, 2026-10-08; contract in `docs/internal/architecture/tasks.md`) are a control plane separate from observation. A change that widens exposure updates this rule in the same pull request. Task text, the agent-judged own condition, and feature names are user-authored content, a data class held only in a private, versioned, bounded, monitor-owned task store (per repository 500 tasks and 50 features; task text 4000 characters, own condition 500, feature name 80, block reason 200), separate from the observation cache and its retention and prune cycle. A malformed or newer store is never overwritten by a routine write. As decided by the product owner on 2026-10-09, a board has exactly five fixed columns (Backlog, Ready, In progress, Review, Done, in that order), and no action adds, renames, deletes, reorders, or re-roles one. In progress, Review, and Done always hold the fixed roles `in_progress`, `review`, and `done`, and Backlog and Ready hold none; the roles are kept in the same task store, and `GET /api/tasks` serves a role beside the fixed column name and nowhere else. A store made before this rule is brought to the five columns in one task-store write, when the monitor opens the store or on the first read or action for the repository: a column that matches one of the five by its role or its name maps to it, the cards of any other column move to Backlog after the cards already there, and no task is dropped. The monitor moves a task's card to the role's column only inside the task-store write that persists the session link, a report verified as Needs review or Done, or the user's Mark done, never from an observation, so no move is taken back. That content is served only by the no-store `GET /api/tasks?repositoryId=` (a committed-store read that never acquires provider evidence) to a same-computer client gated like `GET /api/provider-folders`, and by trusted desktop IPC. The LAN gateway never forwards it, and a denied client receives `readiness: "desktop_only"` with no task content. It never enters `/api/state`, session catalogs, reports, logs, notifications, diagnostics, or checkpoints. The one widening that has shipped is the Sessions list: `GET /api/sessions?mode=directory` may join, at serving time and from the task store alone, a nullable `task` onto each row, holding only the task ID, the ID of the repository whose board holds it, a task state limited to `needs_review`, `stalled`, `blocked`, `done`, or null, the opaque feature ID, the feature name, the step, and, as the one field added by the product owner's decision of 2026-10-09, the nullable number (1 to 999999999) of the GitHub issue the task was promoted from, read from the task store's source row alone. It is never written to the session catalog, a checkpoint, or the shell feed, and never carries task text, the own condition, a column name, a report, a block reason, or an issue title or body. The same read may take a `feature` scope (one feature ID) and `group=feature`; the catalog index then receives only a bounded set of session IDs, never task data, and a feature scope that cannot be answered matches no session instead of every session. Task references are served like `GET /api/tasks`, to a same-computer client only: the same-origin proxy sets the `tasks=1` marker itself and never copies it from the request, the LAN gateway marks every request it forwards (`x-pomegr-lan-gateway`) so a forwarded request is never marked, and the monitor also requires its same-computer read gate. Any other client gets the list with `taskReadiness: "desktop_only"`, no `task` key, and no feature name. The session view has no projection of its own: it reads its own row through the same directory read with a `session` scope (one validated session ID, excluding every other scope), under the same gate and with the same fields, and reads the task itself only from `GET /api/tasks`; nothing about a task enters `/api/state` or a session domain. User mutations and session starts happen only in the desktop app: renderer, then the fixed IPC channel `pomegr:task-action` (trusted main frame only; a closed list of fixed action names, the repository ID pattern, and a 16 KiB payload cap), then desktop main, then `POST /internal/tasks/<action>` with the desktop token, where the monitor validates the record. A manual session start uses the separate fixed channel `pomegr:task-start` (trusted main frame only; a repository ID and a task ID in, one fixed status out) and the desktop-token routes `POST /internal/tasks/start-plan` and `start-abort`; the plan's repository root, prompt, and dispatch token stay in desktop main, and the monitor stores only the token's digest and mint time. A third fixed channel, `pomegr:task-worktree-open` (trusted main frame only; a repository ID and a task ID in; one fixed status out of `opened`, `not_found`, `invalid`, `unavailable`), opens a task's existing worktree folder in the file manager, only when the folder exists and Git lists it on the task branch; the path is resolved and opened in desktop main and never leaves it, and the task modal's Open folder after a `worktree_dirty` start and the queue banner's use this same channel. Browser and LAN clients never mutate tasks or start sessions. The queue is off by default for each repository and is turned on or off only by the `queue_settings` action. Scheduling adds two kinds of time, each one instant held in the task store and set only through the same desktop actions: a task's own start time (`queue_add` with `at`, state Scheduled), before which the task is started neither by the queue nor by hand, and the queue's start and stop times (`queue_settings` with `schedule`), outside which the queue runner is answered no start. A time is judged only when a start is asked for, with the monitor's clock, so scheduling needs the desktop app open; a time that passed meanwhile counts from the next ask, and only while the stop time has not come. A schedule holds starts like a gate: it writes nothing, pauses nothing, and never stops or touches a running session. `GET /api/tasks` may carry `queue.schedule` with only those two instants or null, and the fixed hold reasons `before_queue_start` and `after_queue_stop` for the queue's next task. With it on, the desktop queue runner polls the desktop-token route `POST /internal/tasks/queue-next` on a bounded low-priority interval; the answer holds at most 16 repository ID and task ID pairs and no task content, and the next start is never served on `GET /api/tasks`. The runner starts the queued tasks of one step together, one after another through the same dispatcher, and a start that does not succeed pauses the queue through `POST /internal/tasks/queue-pause` instead of being retried. A task of a step that holds more than one task starts in a Git worktree of its own under a Pomegr-owned directory of the desktop data root (`<repository ID>/<task ID>`, branch `tasks/<task ID>`), made by desktop main with `execFile` and argument arrays; the monitor's start plan carries only a `worktree` boolean, and the worktree path stays in desktop main, never in the monitor, the task store, browser state, a log, or a report. Pomegr never removes a worktree that has uncommitted changes or a commit that exists nowhere else, and never forces a removal. A requeued task's worktree is reused only when Git lists it on the task branch with a clean working tree; uncommitted changes fail the start with the fixed `worktree_dirty` (a manual start's status, and the queue's pause reason), while a `git status` that itself fails stays an ordinary failure. `GET /api/tasks` may carry `queue.pauseReason`, one fixed value (`cli_missing`, `plugin_missing`, `unsupported_platform`, `start_failed`, `session_not_linked`, `worktree_dirty`) or null, never a path, command, or error text. `GET /api/tasks` may additionally carry `runModels`: at most 64 validated Codex client-catalog model identifiers with their safe labels, from the last committed catalog held in memory, never entitlement, hidden or alias IDs, raw catalog rows, or a catalog read triggered by the GET. Agents get exactly three write paths, `POST /api/agent/v1/tasks/add|complete|block`, authorized like the agent-query GETs; they are the first agent writes and need this rule updated before any other is added. Each call is bound to the calling session by the harness (Claude Code `PreToolUse` hook, which adds a `session_proof` (an HMAC over tool, session, and issue time, keyed by the local agent-query capability, valid for 10 minutes) that the MCP server verifies at call time and refuses the call without, so hooks that are off or time out leave the call refused; Codex the thread identity the host puts in each MCP tool call's `_meta`, with `CODEX_THREAD_ID` as the fallback), never by a model-supplied value. The plugin's session-start hook has one more write, `POST /api/agent/v1/tasks/bind`, with the same authorization: it carries only the dispatch token and the hook-provided session ID, is never a model tool, and answers one fixed `not_found` for a wrong, reused, or expired token, an already linked task, and an already linked session, with no task or repository content. The link is single-assignment, the token's digest is discarded once it is bound, and a linked task is never started again unless the user requeues it (`resolve_requeue`), which clears the link and the report. `add_task` targets the repository of the task the bound session is linked to (read from the task store alone), falling back to the session's committed repository identity only when the session is not linked, and accepts no path or repository ID. A started session carries an opaque random dispatch token (`POMEGR_TASK_TOKEN`) in its environment; the plugin's session-start hook reports token and session ID to link task and session, and `complete_task` and `block_task` act only on the task linked to the bound session: they take no task or repository input, a task takes one report per dispatch, and their answers carry only the resulting state and each checked condition's pass or fail. The token never reaches browser state, logs, or reports. Pomegr verifies checked done-when conditions monitor-side from committed facts (the bound session's committed repository and pull-request state in memory, with no Git, GitHub, or provider read; an unknown fact never passes, and a fact read before the session's latest work that could have changed it is unknown) and exposes only per-condition pass or fail, a bounded block reason, and times, never command output, diffs, or provider payloads. For the CI passed condition only, the monitor's existing bounded pull-request read may also ask GitHub for the pull request's check list and keep, in monitor memory alone, one fixed aggregate status (`passed`, `failed`, `pending`, or `none`) for at most 256 pull-request URLs. That status is never persisted, never joins the normalized pull-request item, and never enters `/api/state`, a session domain, a repository snapshot, a report, a log, or `GET /api/tasks`; check names, URLs, conclusions, and counts are dropped at normalization. Only `passed` on the task branch's pull request passes the condition: pending, failed, no check, and an unread status do not. The monitor keeps that status together with the time of the read that established it, in memory only and for the same at most 256 pull-request URLs; the time is used only to refuse a pass on a fact read before the session's latest relevant work, is never persisted, and never joins the normalized pull-request item or any served surface. The committed repository and pull-request blocks of a live session state also carry a monitor-private `readAt` (the start of the Git read, and the start of the oldest pull-request read). They are removed by the session-state serializer before any serving, and never appear on `/api/state`, a session domain, a repository snapshot or sidecar, a checkpoint, a report, a log, or `GET /api/tasks`. The agent's report alone completes a task only when no condition is checked; report-less completion is not implemented. A task has no liveness state of its own: its card borrows the bound session's observed state, and no state is shown and later retracted. The monitor sets a linked task with no report to Stalled once, from committed session facts in memory that establish the end (catalog state Closed; Stopped for a Claude Code session; Stopped or Unknown with the Codex writer released; never Idle, Open, a bare Unknown, or Stopped of an unrecognized provider), and persists only that state; a stalled task, and a linked task whose session has not reported, leave their state only through the user's Mark done or Requeue. Nothing marks a linked task with no established end Done or Stalled by itself, the queue never advances past it by itself, and neither action stops, attaches to, or writes to a session. For a linked task, `GET /api/tasks` may carry `session` with only the normalized session ID, the bounded catalog title, the session's fixed catalog state, and the primary agent's latest reported model identifier (validated like the request model identifier), all read from already committed session facts in memory; until those facts are committed the state is `unknown` and the card keeps the task's own chip. A manual start needs an explicit native confirmation, and the queue runner starts without a prompt only after the user turned the queue on; every start first passes the start gates (previous step done, provider usage capacity, no provider incident, clean working tree) evaluated from committed facts: the committed usage response and public provider status in memory, and a monitor-private working-tree observation of the recognized repository root that is refreshed off the request path (an ask may queue one asynchronous Git status; it never waits for it), held in memory for at most 16 repositories and never persisted. A missing, stale, or partial fact is unknown and holds the start like a failed gate. A held queued start writes nothing and the task waits; a held manual start answers the fixed `gate_held`. The usage threshold is a fixed choice (70, 85, or 95 percent of the five-hour window, default 85) per repository, changed only by the `queue_settings` action. `GET /api/tasks` may carry `queue.gates`: the threshold, per provider a fixed usage status with the whole five-hour and seven-day percentages Usage limits already shows and a fixed provider-status value, a fixed working-tree value (`clean`, `dirty`, `unknown`), and for the queue's next task its ID, provider, the ID of the earlier task it waits on, and fixed hold reasons; never a root, changed file, reset time, incident detail, or error text. A start opens a visible terminal in the repository root or a task worktree with `spawn` and an argument array (`shell: false`); task text is untrusted and is never interpolated into a command line or path, the session prompt is a fixed template, the Pomegr plugin must be installed in the repository at a version that has the task hook and tools (an unknown version never passes) or the start is refused with the fixed `plugin_missing`, and platforms other than Windows answer a fixed `unsupported_platform` result. A running session is never stopped by Pomegr, a schedule, or the queue, and scheduling needs the desktop app open.

## Metric conventions

- “Context” means the latest non-zero usage snapshot, not historical throughput.
- “All-agent context” is the sum of each visible agent's latest context snapshot.
- Present context only as latest snapshots or sums derived from them. A bounded request-snapshot feed may present independent request-local observations, but must never bucket, carry forward, delta, or sum them across requests or agents. Never derive or present cumulative transcript throughput, token-spend totals, or recent token rates. A provider-reported cumulative session-cost estimate captured from Claude Code's status-line feed is the sole exception and must remain explicitly labeled as an estimate.
- Context-history timelines must carry each visible agent's latest non-zero snapshot to each bucket boundary and plot the bounded actual context level for the selected agent or the explicit sum of agent snapshots. Repeated snapshots stay flat and context reductions remain visible; never reinterpret the series as throughput, unique shared memory, token spend, or cumulative usage.
- Cache-event views must be built monitor-side from bounded, provider-comparable usage observations and expose only recognized refill, reuse, cautious miss-refill evidence, a cache-expiry inference supported by a preceding resolved request lifetime and matching provider-neutral unavailable-entry status, or a fixed tool-definition attribution supported by a documented structural lifecycle rule, which for newly recorded deferred definitions may add only a bounded count and never a tool name. Rules operate independently within each normalized agent, including subagents and forks after they have comparable prior evidence. Missing, malformed, incomplete, incomparable, ambiguous, or unsupported evidence must degrade to unavailable; never infer an unsupported cause, bill, charge, or savings amount.
- Cache-read-drop evidence requires explicit numeric provenance and adjacent requests from the same normalized agent and comparison group, a high-to-low cache-read-share transition, and an actual cached-token collapse. Missing or malformed evidence, compactions, context reductions, and comparison-group changes break comparisons. A model change breaks the same-model possible-refill inference but may yield the bounded `model_change` observation when all other gates pass; that kind carries no refill, expiry, or causation inference. It must never relax the recorded-write requirement for refill classification or turn a minimum-only cache lifetime into an expiry threshold.
- Label elapsed duration as wall time because it includes idle gaps.
- Document heuristic changes in `docs/internal/architecture/metrics.md`.
- Rule-generated recommendations must trace to concrete events.

### Codex on Windows

- In a managed Codex filesystem sandbox, run `npm run build` with escalated sandbox permissions because it overwrites the generated plugin bundles under `plugins/claude-code` and `plugins/pomegr`. A sandboxed run can report `Access is denied` or `EPERM` for a bundle even when Windows has no open handle or ACL restriction; do not diagnose that message as a process lock without independent handle evidence.
- `npm test` runs only `test:node` and `test:ui` without building, so it can remain sandboxed. `npm run verify` includes the build and needs the same escalation.
- Do not run `npm run build` and `npm run verify` concurrently. Both regenerate the same plugin bundles.
